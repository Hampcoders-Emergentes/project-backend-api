## Decisión e implementación

Se añade `AllowEdgeApiKeyAttribute` como metadata de una alternativa de autenticación de máquina. El middleware solo acepta una clave válida si el endpoint seleccionado tiene esa metadata **y no tiene** `AuthorizeAttribute` propio, `RequireAccessRoleAttribute` o `IAuthorizeData` del framework. Ante esos requisitos humanos sigue el camino JWT, consulta el usuario y carga `Items["User"]` / `Items["AccessRole"]`, aunque llegue X-Api-Key. No se fabrica un principal humano a partir de una clave.

`RequireEdgeApiKeyAttribute` deriva de esa metadata, conservando sin cambios su filtro de clave obligatoria y sus respuestas. Se aplica `AllowEdgeApiKey` **solo a GetRelayHistory**, sin habilitar el controller completo ni decidir por prefijo de URL. En history, clave Edge o JWT humano siguen siendo alternativas; con una clave válida se permite el canal de máquina incluso si un JWT adicional no es válido. En endpoints con requisitos humanos ese JWT no puede sustituirse por la clave.

No se modifica la validación JWT existente, excepciones anónimas, roles, políticas de pertenencia, payloads, esquema, paquetes, framework ni configuración de despliegue. El requisito de credenciales se endurece deliberadamente en rutas que antes dependían del bypass global no autorizado. Consumidores legítimos comprobados mantienen método, ruta y forma de respuesta.

| Endpoint / composición | Solo clave Edge válida | JWT humano válido + clave válida | JWT humano sin clave / clave incorrecta |
|---|---|---|---|
| GetRelayHistory real | 200 con historial sintético | Acceso por canal de máquina explícito | 200 por canal humano |
| Cuatro acciones reales de EdgeIngestionController | Superan autorización | Superan autorización | 401 del filtro Edge |
| Sondas humanas y de roles | 401 | Usuario cargado; rol permitido 200, insuficiente 403 | Continúa validación humana |
| RequireEdgeApiKey + requisito humano propio/framework | 401 | Ambos requisitos satisfechos | 401 del filtro Edge |
| Rutas reales vecinas de history | 401 antes de los servicios | Siguen camino JWT; la acción conserva su lógica | No se concede acceso de máquina |
| Ruta sin metadata o sin endpoint seleccionado | 401 sin token humano | No se concede excepción Edge | Sigue el camino previo de token |

Para las acciones Edge, “superan autorización” es una observación del pipeline, no una ejecución de negocio ni un 204 de ingesta demostrado: un filtro de recursos **solo de pruebas**, posterior a autorización, devuelve 204 con el nombre de la acción seleccionada antes de activación/model binding. Impide ejecutar servicios de ingesta, altas demo, ack, thresholds o relés. Los rechazos no alcanzan ese centinela.

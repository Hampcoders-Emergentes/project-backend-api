## Algoritmo real ejecutado y efectos en orden

`Processing/Application/Internal/EventHandlers/ConsumptionThresholdsUpdatedEventHandler.cs`:

1. Lee los umbrales y aplica sus defaults actuales cuando faltan claves; convierte decimal a float/int. Las pruebas usan las ocho claves explícitas, sin modificar defaults ni validar rangos adicionales.
2. Construye UpdateCustomThresholdsCommand y llama al servicio real DeviceReadingStreamCommandService.
3. El servicio busca por ClientIdentity del propietario; para cada stream crea ThresholdConfig, asigna CustomThresholds y llama UpdateAsync. Después llama UnitOfWork.CompleteAsync **incluso si no encontró streams**.
4. Tras terminar el servicio, el handler busca el ID fijo `dev-electrolink-esp32-01`. Si existe, asigna umbrales, llama UpdateAsync y realiza un segundo CompleteAsync, sin comprobar que Owner coincida con el evento.

El agregado UpdateCustomThresholds solo asigna el nuevo valor. En esta ruta no se llama PublishAndClearEvents y no se emiten eventos de dominio adicionales. El repositorio EF marca Update y UnitOfWork delega en SaveChangesAsync; sus efectos SQL/interceptores no se ejecutan aquí. El handler no utiliza EventId/UpdatedAt para deduplicar u ordenar.

## Resultados observados

### Primera entrega y repetición equivalente (3 casos)

Se serializa/deserializa el evento para la segunda entrega. Se comprueban distinto objeto y diccionario, mismo EventId, OwnerId, UpdatedAt, OccurredOn y contenido. La nueva entrega carga las copias confirmadas por la anterior.

| Demo | Updates por entrega | Guardados confirmados por entrega | Cambios de valores en primera / segunda entrega |
|---|---:|---:|---:|
| Ausente | 2 | 1 | 2 / 0 |
| Otro propietario | 3 | 2 | 3 / 0 |
| Mismo propietario | 4 | 2 | 3 / 0 |

Siempre se repite el comando al servicio y se conserva el orden de llamadas. Si demo pertenece al propietario, el servicio lo actualiza junto con los demás y el handler vuelve a actualizarlo y guardar. Si pertenece a otro propietario, igualmente recibe los nuevos umbrales: **brecha de alcance**, no decisión aceptada del dominio. El stream ajeno distinto del demo conserva sus valores.

Los valores finales toleran la reasignación idéntica en este modelo, pero no se deduplican llamadas o guardados. No se generaron eventos de dominio ni llamadas al publicador en esta ruta; eso no demuestra ausencia de efectos de auditoría/interceptores al ejecutar EF real. No se prueba resistencia a una reentrega antigua después de otro evento con valores nuevos.

### Fallos y reentrega (5 casos)

La excepción sintética original sale del handler sin ser envuelta o absorbida. La traza se detiene en el punto de fallo y las aserciones comprueban que no hay efectos posteriores. En todos los casos, la reentrega con el mismo EventId es explícita desde la prueba, **no un reintento automático instalado**.

| Punto de fallo | Estado en memoria tras fallar | Guardado simulado | Reentrega desde nuevas copias |
|---|---|---|---|
| Consulta por propietario | Sin asignaciones | 0 intentos / 0 confirmaciones | Aplica propietario y demo; 3 cambios de valores |
| Primer guardado | Dos streams del propietario con nuevos valores; demo intacto | 1 intento / 0 confirmaciones; persistencia conserva defaults | Recarga defaults, vuelve a asignar y confirma ambos pasos; 3 cambios |
| Consulta demo, después del servicio | Propietario actualizado, demo intacto | Primer guardado confirmado; propietario nuevo/demo anterior | Repite servicio y guardado con 0 cambios de propietario; aplica demo, 1 cambio |
| UpdateAsync demo | Propietario actualizado; demo ya mutado en memoria antes de fallar UpdateAsync | Solo primer guardado confirmado; demo persistido anterior | Nuevo agregado demo conserva valor anterior, se actualiza y confirma; 1 cambio |
| Segundo guardado | Propietario y demo con nuevos valores en memoria | 2 intentos / 1 confirmación; snapshot del segundo intento muestra demo nuevo, estado confirmado demo anterior | Recarga propietario nuevo/demo anterior y completa; 1 cambio |

La primera frontera puede quedar confirmada aunque falle la segunda. No se inventó una transacción conjunta ni se presentó la memoria como persistencia. Las pruebas no modelan fallos ambiguos de base que confirman y luego pierden la respuesta.

### Propietario sin streams (2 casos)

El servicio completa una vez aunque la selección esté vacía. Con demo ausente no hay updates; con demo de otro propietario hay un update y un segundo guardado. La reentrega repite las llamadas/guardados y produce cero cambios de valores. La ausencia de streams del propietario no impide la escritura sobre el demo ajeno.

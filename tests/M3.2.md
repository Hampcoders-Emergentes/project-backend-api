## Capacidad implementada

Vínculo: POST/GET `api/v1/stores/{storeId}/areas/{areaId}/equipment/{equipmentId}/device-binding`. POST recibe únicamente deviceId interno y edgeDeviceId; devuelve 201 con Location. GET devuelve identidad interna, serie, ID Edge canónico, equipo, LinkedAtUtc y procedencia de umbrales. Se exige identidad humana IAM y toda la ascendencia del equipo. No se modifica la asignación/instalación heredada. Cada equipo y dispositivo tiene un vínculo único; también es único el ID Edge. No hay traslado/desvinculación automática.

Consulta: GET bajo el mismo equipo, sufijo `/telemetry`, devuelve último registro y estado. UNKNOWN sin lectura; NORMAL/ANOMALY solo con última captura fresca y autoridad verificada; STALE para datos atrasados; DEVICE_UNVERIFIED si la autoridad actual dejó de acreditarse. El tipo/severidad de detección guardado es histórico, sin reconocimiento/resolución de alerta.

Entrada: se preservan POST `/api/v1/iot/edge/readings`, IngestReadingResource, aliases EdgeDevice/EdgeBufferReplay/EDGE y 204 aceptado. Un reenvío idéntico devuelve 204 sin duplicar; ID repetido con payload distinto devuelve 409. Los campos adicionales como currentIna siguen ignorados. Para el vínculo se exige clave válida y alcance exacto `EdgeApi:EquipmentReadings:AllowedDeviceIds`, separado del alcance relay/history. No se modificó appsettings/.env ni se habilitaron IDs reales.

Umbrales: GET `/api/v1/iot/edge/devices/{deviceId}/thresholds` conserva forma/ruta y entrega el snapshot del vínculo antes de entrar a la rama heredada demo. Los valores proceden explícitamente de Processing.ThresholdConfig.Default:v1, guardados al vincular; son un puente MVP, no umbrales personalizados o sincronización versionada completa.

El nuevo servicio nunca crea streams, locales o propietarios demo. Un ID vinculado sin alcance o con prueba revocada devuelve 403 y no cae al legado. Un alias alternativo conocido de ese dispositivo o un ID reservado en alcance nuevo sin vínculo también se deniega. Para IDs ajenos al recorrido nuevo se conserva el legado, incluidos sus problemas previos de defaults demo/actuación: no se presentan como corregidos ni como comportamiento seguro aceptado. No se afirma compatibilidad de todo Edge desplegado; relay/history sigue con su contrato y alcance M2.3, y no se ejecutó Edge.

Identidades: deviceId interno, serialNumber y edgeDeviceId se conservan separados y se relacionan solo mediante inventario Assets verificado. edgeDeviceId debe coincidir exactamente con ID interno o serie, sin normalización. También se rechaza una serie que colisione con otra identidad. StoreId no se asigna a PropertyId y UserId no se transforma en ClientIdentity por parecido. La propiedad heredada queda como evidencia, no como local nuevo ni prueba de traslado físico.

## Medición y reglas sin efectos físicos

Se guardan BindingId, ReadingId, captura UTC, recepción UTC, base temporal, V, A, PF, Hz y origen exacto. Se reutiliza Reading.Create para rangos y cálculo de kW; el objeto Reading de adaptación es temporal y su clave de proyección no se consulta o persiste como un StreamId heredado; se añaden rechazo de no finitos, fecha inválida/futura y límites de identificadores. No se inventan temperatura, corriente residual o energía acumulada.

El Edge inspeccionado genera UTC; un timestamp con offset conserva ese instante normalizado, y uno sin offset se interpreta como UTC con marca EDGE_UTC_ASSUMED porque la persistencia Edge puede perder la zona. La marca mantiene visible esa suposición. No se convierte uptime del ESP32 en fecha ni se afirma que un reloj real esté sincronizado. La política de desfase aún necesita validación operativa.

La última muestra se ordena por captura, no por recepción. Se usa DisconnectionThresholdMin del snapshot (10 minutos en Default:v1) como ventana explícita de frescura. Una lectura atrasada se guarda y no se evalúa como actual. Para detección fresca se toman hasta 120 muestras anteriores/inclusiva a la captura, con las reglas existentes de Processing.

ElectricalAnomalyRules contiene exactamente el cuerpo de DetectAnomaly anterior, verificado contra la copia inicial. AnomalyCommandService ahora delega en esa función, manteniendo su comportamiento; no se cambiaron sus ramas de relé del legado. El nuevo servicio invoca solo la función pura, sin crear AnomalyRecord/Alert ni publicar eventos, MQTT o relés. Una detección crítica consultable no equivale a alerta atendida/resuelta, desconexión física o certificación de seguridad.

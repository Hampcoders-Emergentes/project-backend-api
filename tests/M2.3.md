## Regla y canal autenticado

El middleware coloca una `EdgeApiKeyAuthenticationFeature` interna únicamente después de validar la clave global y seleccionar el canal de máquina según la metadata de M2.1. No contiene la clave, no crea un usuario y no asigna un gateway. La presencia de un header no establece esa feature.

La acción GetRelayHistory conserva AllowEdgeApiKey y añade **solo en ese método** RequireRelayHistoryDeviceAccess. El filtro:

1. Si no existe la feature de máquina, conserva el camino humano ya autenticado por el middleware.
2. Si existe, obtiene deviceId del routing y los hijos de `EdgeApi:RelayHistory:AllowedDeviceIds` del servidor.
3. Exige coincidencia exacta ordinal. Sin lista, vacía o sin coincidencia devuelve **403 antes de invocar el controller/query/repositorio**.

No recorta espacios, no cambia mayúsculas, no acepta comodines y no traduce serie a ID interno. Un ID formado solo por espacios no se autoriza. No se construye la lista desde headers, query strings, telemetría, streams demo o datos enviados por el cliente.

### Precedencia conservada

| Credenciales y alcance en history | Resultado |
|---|---|
| Clave válida + ID permitido | 200, historial normal |
| Clave válida + ID fuera de lista | 403, sin consulta de comandos |
| Clave válida + lista ausente/vacía | 403, sin fallback permisivo |
| Clave válida + JWT humano válido + ID denegado | 403; **no se reintenta por el canal humano** |
| Clave válida + JWT inválido + ID permitido | 200 por el canal de máquina, como en M2.1 |
| Sin clave o clave inválida, sin humano válido | 401 del camino de autenticación existente |
| JWT humano válido, sin clave o con clave incorrecta | Comportamiento humano anterior; no se aplica la lista de máquina |
| ID permitido sin comandos | 200 con commands vacío, UNKNOWN y fecha nula |

Los endpoints con requisitos humanos siguen teniendo precedencia sobre la alternativa de máquina. Los roles y carga de Items["User"] se conservan; B1/B2 no se reabren. No se cambia RequireEdgeApiKeyAttribute ni se impone esta lista a readings, anomalies, acknowledge o thresholds.

## Configuración y compatibilidad

Nombre mínimo: **EdgeApi:RelayHistory:AllowedDeviceIds**, colección en configuración del servidor. Ejemplo **exclusivamente sintético**, no aplicado a configuración de ejecución:

```json
{
  "EdgeApi": {
    "RelayHistory": {
      "AllowedDeviceIds": ["dev-synthetic-history-a", "dev-synthetic-history-b"]
    }
  }
}
```

También puede representarse por nombres de variables `EdgeApi__RelayHistory__AllowedDeviceIds__0`, `EdgeApi__RelayHistory__AllowedDeviceIds__1`, etc., según los proveedores de configuración ya existentes. No se muestran ni cambian credenciales. Para denegar todo el canal de máquina de history, omitir la lista o dejarla vacía; **no existe modo permisivo por omisión**.

No se editaron appsettings.json, .env, .env.example ni configuración de despliegue. Por tanto, un entorno que hoy no declare la lista pasará a denegar history a máquinas si se ejecuta esta versión. **No está habilitada para uso real**: antes deben conciliarse los IDs exactos usados por el consumidor y asignarse responsable y procedimiento de mantenimiento de la lista. No se inventaron ni recopilaron IDs reales.

La ruta, método y payload de las respuestas permitidas se conservan. El cambio deliberado es el 403 para acceso de máquina sin alcance. El Edge existente no necesita una nueva forma de request, pero recibirá 403 si no se configura su alcance legítimo. La tolerancia operativa del consumidor a ese 403 no se verificó ejecutando Edge.

La lista es una autorización explícita de la credencial compartida; **no certifica registro, instalación o pertenencia física**. Una entrada explícita sin comandos sigue dando 200 vacío, aunque no haya un dispositivo registrado en el fixture. No se añadió una consulta de Assets ni una política humana por recurso.

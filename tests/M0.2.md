## Composición y fronteras verificadas

No usa `Program`, `WebApplicationFactory`, archivos de configuración, variables de secretos, conexión de datos, inicialización EF, jobs, MQTT ni proveedores. La única configuración de aplicación es sintética. No hay servicios de persistencia o envío de comandos registrados.

El orden reproducido desde `Program.cs` es routing → JwtBearer → RequestAuthorizationMiddleware → autorización ASP.NET → MVC y sus filtros. Se usan las convenciones de rutas del backend. El handler JwtBearer, `TokenService`, middleware y atributos son los reales; se duplican solamente sus opciones de composición, con claves sintéticas. Fronteras examinadas: entrada Authorization/X-Api-Key → firma y vigencia del JWT → identidad del principal → usuario cargado por consulta → rol del usuario → filtros del endpoint. Se prueba que la credencial de máquina no fabrica identidad humana y se detecta el salto global del middleware. No se prueba pertenencia por local/dispositivo.

## Resultados observados frente a objetivo

| Escenario | Resultado ejecutado | Interpretación |
|---|---|---|
| Sin credenciales: ruta simple, filtro humano, rol o relay/history | 401, `Unauthorized: Missing token`; la consulta de historial no se ejecuta | Rechazo comprobado |
| JWT malformado, expirado o con firma incorrecta | JwtBearer no autentica; middleware devuelve 401, `Unauthorized: Invalid token` | Se comprueban los tres tipos, no solo un string inválido |
| JWT firmado válido, usuario existente | Principal autenticado e `Items["User"]` con el mismo ID | Camino humano comprobado |
| JWT válido, usuario inexistente | 401, `Unauthorized: User not found` | La firma no sustituye existencia de usuario |
| Admin / SuperAdmin en filtro equivalente a staff-users | 200 | Roles actuales permitidos |
| User / Maker / FieldManager en ese filtro | 403 | Roles actuales rechazados |
| Rol JWT distinto del usuario consultado | Decide el rol del usuario consultado | Fuente de rol del filtro propio caracterizada |
| Clave Edge ausente o incorrecta, sin JWT | 401 del middleware | No se alcanza el filtro Edge |
| Clave Edge ausente o incorrecta, con JWT válido | 401 del filtro Edge | Una identidad humana no reemplaza la clave requerida |
| Clave Edge válida en filtro Edge | 200 sin principal ni usuario humano | Identidad de máquina no se convierte en humana |
| Clave Edge sin configurar, con JWT válido | 500 del filtro Edge | Falla cerrado; manejo operativo de configuración pendiente |
| Clave Edge válida en filtros humano/rol/ambos o Authorize del framework | 401 sin JWT humano | No equivale a bypass efectivo de todos los filtros |
| Clave Edge válida con JWT de firma incorrecta | Filtro Edge: 200; filtro humano: 401 | El JWT inválido no crea identidad; el canal Edge sigue siendo independiente |
| JWT válido con clave Edge incorrecta en ruta humana | 200 | Continúa el camino de validación humana |
| JWT válido con clave Edge válida | JwtBearer autentica, pero Items queda vacío; filtro propio 401 y filtro framework 200 | **Brecha B2:** divergencia entre modelos de identidad y regresión ante cabeceras mixtas |
| Clave Edge válida en ruta sin metadata Edge ni filtro humano | 200 sin humano | **Brecha B1:** bypass global, contrario al alcance de credenciales Edge descrito en context.md §8.1 |
| Metadata anónima propia | 200 sin credenciales | Excepción explícita caracterizada |

## Compatibilidad Edge y relay/history

Se comprobaron por metadata las cuatro acciones reales de `EdgeIngestionController` bajo `[RequireEdgeApiKey]`. La matriz HTTP del atributo se prueba mediante sondas; no se ejecutan los servicios de ingesta, altas demo, acknowledge ni thresholds.

Se ejecuta además la acción **real** `GET /api/v1/iot/devices/dev-m02/relay/history`, que está fuera de `/iot/edge` y no lleva el filtro Edge. Con clave Edge válida o JWT humano válido devuelve 200 y JSON con `deviceId`, `currentRelayState`, `lastCommandAt` y `commands`; se verifican un comando sintético ejecutado y sus campos de estado, autor, origen y fecha. Sin credenciales, con JWT inválido o solo con clave incorrecta devuelve 401 antes del servicio doble.

Esta dependencia de la excepción global es importante: restringir el bypass únicamente al prefijo `/iot/edge` rompería el acceso Edge a `relay/history`. Su autorización de máquina debe conservarse mediante una decisión explícita por endpoint, sin autorizar por accidente todas las demás rutas del mismo controller. El backend conserva hoy sus contratos porque M0.2 no modifica código de producción. No se ejecutó el consumidor Edge real y no se certifica su compatibilidad integral.

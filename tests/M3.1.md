### Capacidad y seguridad implementadas

El actor sale exclusivamente de Items["User"] resuelto por el middleware IAM existente. Los endpoints llevan el atributo humano Authorize; no aceptan la clave Edge como alternativa. No se obtiene titularidad de un profileId, HomeownerId, CompanyId, header o cuerpo arbitrario. Store.Register exige UserId; el contexto convierte ese tipo a texto requerido y añade índice (OwnerUserId, Id). No hay propietario por defecto para datos existentes.

El servicio exige local accesible antes de crear o consultar áreas, y área del mismo local accesible antes de operar equipos. El repositorio EF incluye nuevamente el titular mediante Where y joins, incluso en listas. No se infiere permiso por rol Admin o JWT válido. Las respuestas son DTO separados de EF; las listas están limitadas y no devuelven inventario global.

POST devuelve 201 y Location; GET devuelve 200. Los cuerpos solo aceptan name/address para Store o name para Area/Equipment; propiedades desconocidas, incluido ownerUserId, se rechazan con 400. Names de máximo 120 y dirección de máximo 300. Páginas por defecto 1/20, tamaño de 1 a 100 y offset dentro de Int32; orden por ID, hasMore sin conteo global. 401 para credenciales ausentes o solo máquina; 404 para inexistencia, titular ajeno o ascendencia incorrecta; 400 para entrada/IDs/paginación inválidos. POST no ofrece idempotencia y no debe reintentarse automáticamente tras resultado ambiguo. No hay cambio de titular, traslado, actualización o eliminación en M3.1.

Las nueve rutas y DTO están documentados en StoreManagement/Interfaces/REST/README.md. Ninguna ruta o ID heredado se renombró. La corrección de umbrales ajenos y las protecciones B1/B2, history y cancelación outbox permanecen intactas.

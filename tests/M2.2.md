## Primera regla propuesta y fuente de verdad

Propuesta transitoria recomendada al usuario: para el canal de máquina en **GET relay/history**, exigir autenticación global válida **y** que el deviceId exacto pertenezca a una lista explícita de dispositivos autorizados **en el servidor**. No obtener la lista de headers, query strings, lecturas recibidas o recursos demo. Sin lista o fuera de ella, denegar antes de consultar comandos; no usar un fallback que permita todo. Mantener separado el camino humano actual y no convertir la clave en usuario.

La lista sería una fuente de autorización explícita, administrada por el responsable del backend, conciliada con el inventario legítimo. Assets.IoTDevice / AssignedPropertyId / Property.Owner son fuentes del inventario y la asociación física heredada, **no una autorización de gateway ya existente**. Antes de cargar la lista hay que confirmar cuáles IDs consume history y su correspondencia con el inventario; no inferirla del nombre ni traducir serie/ID silenciosamente.

Datos necesarios para esa primera corrección: lista exacta por entorno del alcance permitido a la credencial compartida, responsable de mantenerla, correspondencia de IDs externos/internos y comportamiento definido para configuración ausente. Ningún valor real se recopila o registra en este documento. La regla propuesta devuelve 403 tras autenticación de máquina válida cuando el recurso queda fuera de alcance; conserva 401 para credencial inválida y 200 con historial vacío para un dispositivo autorizado sin comandos. Si se desea exigir también registro/estado instalado o devolver 404, debe especificarse antes: no se mezcla con la primera lista de alcance.

Con esto se puede reducir el alcance de **una credencial compartida**, sin nuevas tablas ni cambios inmediatos en el Edge. No permite distinguir dos gateways que tengan la misma clave, ni evita que cualquiera de ellos lea todos los dispositivos de esa lista. No debe presentarse como aislamiento multigateway o multilocal completo.

### Alternativas y decisión pendiente

| Alternativa | Beneficio | Dependencias / consecuencia |
|---|---|---|
| A. Alcance explícito para la clave global en configuración del servidor | Cambio pequeño, sin esquema ni consumidor nuevo; apropiado como puente | Alcance compartido por todos los poseedores de esa clave; lista conciliada y administrada |
| B. Reutilizar credenciales individuales de IoTDevice | Ya existe hash; limita una credencial a un dispositivo | Resolver ID/serie, provisionamiento/rotación y compatibilidad: el Edge actual usa una clave única para todos |
| C. Gateway identificable con dispositivos asignados | Permite alcance independiente por gateway y relación deliberada con locales | Diseñar cardinalidades, fuente autorizada, credenciales, persistencia y alta/revocación; fuera del alcance actual |

El usuario pidió cuál conviene ahora; se recomendó **A como puente**. Esa consulta no se registra como aprobación de implementación ni de IDs concretos. Decisión material pendiente: adoptar o no esa transición y definir quién mantiene el inventario/lista. La identidad de gateway a largo plazo y la futura pertenencia humana a Store/organización se resuelven por separado.
